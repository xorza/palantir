# Repository review

**Evidence:** “Reproduced” means a small executable exercised the library through public APIs and `UiHarness`. “Source trace” means the finding follows from the cited implementation, and “derived” gives the calculation. ## Dock validation and mutation do not preserve the model's invariants

- [ ] **High — Persisted group-ID allocation state is accepted without validation.** Source trace: `next_group` is deserialized, but [DockState::validate](/home/xxorza/Projects/palantir/src/widgets/dock/dock_state.rs:525) checks only existing groups and tree structure. [Splitting](/home/xxorza/Projects/palantir/src/widgets/dock/dock_state.rs:365) uses the counter as an ID and increments it unchecked. A valid single-group state with group 0 and two tabs still passes validation after its serialized `next_group` is changed to 0; the next split creates duplicate group IDs. `u64::MAX` also passes validation and makes the increment overflow. Validate or derive the allocation state at the untrusted-data boundary so a successfully validated document remains safe to mutate.

- [ ] **High — retain_tabs can remove the tab that guarantees the dock exists.** [DockState::retain_tabs](/home/xxorza/Projects/palantir/src/widgets/dock/dock_state.rs:401) applies the predicate to the pinned tab even though other mutation paths refuse to close it. Reproduced with pinned tab 0 and other open tabs: `retain_tabs(|tab| tab != 0)` returns a state for which `validate()` reports `MissingPinnedTab`; `primary()` can subsequently panic. Filtering every tab instead reaches `normalize`'s nonempty assertion. Preserve the pinned-tab invariant through this public mutation as well.

- [ ] **Medium — Removing an earlier tab changes the active document even when that document survives.** [TabGroup::remove_tab](/home/xxorza/Projects/palantir/src/widgets/dock/tab_group.rs:33) removes the slot and only clamps the old active index. Reproduced with tabs `[0, 1, 2, 3]`, active tab 2, and `CloseTab { tab: 1 }`: the active document becomes 3. [retain_tabs](/home/xxorza/Projects/palantir/src/widgets/dock/dock_state.rs:401) has the same index-preservation problem. Preserve active tab identity across removal/filtering; select a neighbor only when the active tab itself is removed.

## Text entry is reduced to shortcut key identity

- [ ] **High — The host drops committed text that cannot be represented by one logical-key character.** Source trace: [winit input translation](/home/xxorza/Projects/palantir/src/host/winit/input/mod.rs:87) ignores `KeyEvent::text`; [logical_key](/home/xxorza/Projects/palantir/src/host/winit/input/mod.rs:163) takes only the first character, and [TextEdit](/home/xxorza/Projects/palantir/src/widgets/text_edit/input_pass.rs:213) inserts that character. Winit explicitly distinguishes produced text from logical keys, including Windows dead-key fallbacks that produce two characters. That text is lost even without enabling IME. The host also neither enables IME nor handles its committed/preedit strings. Give committed text its own input path, preserving the complete string and keeping command matching on key events. See the primary contracts for [KeyEvent::text](https://docs.rs/winit/0.30.13/winit/event/struct.KeyEvent.html#structfield.text) and [Ime](https://docs.rs/winit/0.30.13/winit/event/enum.Ime.html).

## GPU callback initialization belongs to a texture target instead of the callback

- [ ] **High — Replacing a GpuView renderer can call paint before its init.** Source trace: [GpuViews::record](/home/xxorza/Projects/palantir/src/renderer/gpu_paint/gpu_views.rs:51) replaces the callback for an existing widget ID while retaining its texture identity. [GpuViewTargets::paint_gpu_views](/home/xxorza/Projects/palantir/src/renderer/backend/gpu_view_targets/mod.rs:68) gates `init` on the retained target's `initialized` flag, so a new `Rc<RefCell<T>>` recorded at the same widget ID receives `paint` without initialization, even with the default `repaint(true)`. With `repaint(false)`, the old pixels can also survive the replacement. Track callback identity/lifetime explicitly and make replacement initialize and invalidate the appropriate content; texture retention alone does not establish that the current callback is initialized.

## Image filtering happens before the required alpha and boundary operations

- [ ] **Medium — Bilinear image sampling introduces dark or colored fringes at transparent edges.** Derived from [raw image upload](/home/xxorza/Projects/palantir/src/renderer/backend/image_store.rs:90), the [linear sampler](/home/xxorza/Projects/palantir/src/renderer/backend/texture_binding.rs:61), and [the image shader](/home/xxorza/Projects/palantir/src/renderer/backend/image_pipeline/image.wgsl:75): straight-alpha texels are interpolated before premultiplication. Halfway between opaque red `(1,0,0,1)` and transparent black `(0,0,0,0)`, the current path produces premultiplied `(0.25,0,0,0.5)`; filtering premultiplied inputs gives `(0.5,0,0,0.5)`. The footprint-tap path premultiplies each already-filtered sample, so it retains this error. Establish premultiplied filtering in linear color space before interpolation, with a consistent sampling contract.

- [ ] **Medium — Tiled images clamp within each bilinear footprint instead of filtering across tile boundaries.** Derived from [the ClampToEdge sampler](/home/xxorza/Projects/palantir/src/renderer/backend/texture_binding.rs:61) and [the shader's fract wrapping](/home/xxorza/Projects/palantir/src/renderer/backend/image_pipeline/image.wgsl:155). Wrapping the sample coordinate does not wrap the adjacent texels that bilinear filtering reads. For a two-texel opaque black/white tile, a sample exactly at a repeat boundary returns black under clamping; a repeating bilinear sample blends the last and first texels to 0.5 linear gray. The same boundary error affects each footprint tap. Repeating image draws need repeat addressing at the filter level, while nonrepeating crops need their existing edge behavior.

## Widgets use response data that cannot represent the interaction they offer

- [ ] **Medium — Partially clipped tabs do not cause the overflow button to appear.** [overflow_menu](/home/xxorza/Projects/palantir/src/widgets/tabs/tab_strip.rs:491) compares the band's clipped response rectangle against chip response rectangles that have already been clipped to that band. Reproduced with a 120 px strip, two 80 px chips, no gap/padding, and `TabOverflow::Menu`: the second chip has layout width 80 and response width 40, but no overflow button is recorded. Determine visibility from full transformed chip bounds or the scroll extent, retaining the clipping information the decision needs.

- [ ] **Medium — Dock overflow-menu selection is discarded.** Source trace: [TabStrip's overflow menu](/home/xxorza/Projects/palantir/src/widgets/tabs/tab_strip.rs:537) reports a chosen entry through `hits.clicked`. [DockCtx::strip](/home/xxorza/Projects/palantir/src/widgets/dock/dock_view.rs:286) consumes only `.keyed`, assuming the earlier navigation scan already handled pointer activation. [That scan](/home/xxorza/Projects/palantir/src/widgets/dock/dock_state.rs:661) observes chip and close-button IDs, not popup entry IDs. Choosing a menu entry therefore closes the popup without generating `ActivateTab`. Unify activation delivery, or explicitly carry menu activation into the dock operation queue without duplicating chip clicks.

- [ ] **Medium — show_when_disabled cannot enable tooltips for ordinary disabled widgets.** [Tooltip::show](/home/xxorza/Projects/palantir/src/widgets/tooltip/mod.rs:154) requires `snapshot.state.hovered` even when the option is enabled. [Cascade](/home/xxorza/Projects/palantir/src/scene/cascade/engine.rs:476) removes disabled nodes from hover sensing, so their ordinary responses cannot satisfy that condition. Reproduced with a disabled button, pointer inside its rectangle, zero tooltip delay, and `.show_when_disabled(true)`: no bubble is recorded. The input/public response contract needs an observation path for disabled hover that does not enable the disabled widget's actions.

## Built-in widgets depend on capabilities unavailable through the public API

- [ ] **Architectural — Several widgets cannot be reimplemented externally as required by the project contract.** Source trace: [GpuView](/home/xxorza/Projects/palantir/src/widgets/gpu_view/mod.rs:111) calls crate-only `Ui::gpu_view`; [Scroll](/home/xxorza/Projects/palantir/src/widgets/scroll/mod.rs:422) rewrites private node layout state and uses crate-only `Ui::scroll_content`. Both are capabilities with no public spelling at all, unlike `TextStyle::metrics_valid`, which an outside widget could re-derive from the public fields. Define documented public operations for the capabilities the widgets actually require, then make the built-ins use those same operations. The scroll layout mutation in particular needs a supported authoring operation rather than exposing internal node storage wholesale.

## Spring integration approximates a system with a closed-form transition

- [ ] **Precision and simplification — The adaptive Euler loop adds frame-partition error and numerical parameter restrictions that the spring model does not require.** [spring::step](/home/xxorza/Projects/palantir/src/animation/spring.rs:69) chooses up to 256 substeps and repeatedly applies generic value arithmetic; its validation carries stability margins and an integration-budget limit. For the implemented equation `x'' + damping*x' + stiffness*(x-target) = 0`, with the target held constant during a step, the underdamped, critically damped, and overdamped transitions have closed forms. Use a numerically stable analytical transition to remove the substep loop and its numerical stability restriction while retaining deliberate settling/convergence policy. This promises frame-partition independence up to floating-point error for a fixed target, not a measured speedup. [Ryan Juckett's original derivation](https://www.ryanjuckett.com/damped-springs/) gives the transition and its assumptions.
