# GPU compatibility and performance review

Reviewed on 2026-09-06 against the current checkout, its wgpu 30.0.0 dependency, and primary documentation from wgpu, Khronos, Apple, Microsoft, NVIDIA, and AMD. Scope: GPU selection, capabilities, resource lifetimes, pipelines, uploads, texture filtering, and presentation. Android and browser observations identify additional requirements for extending hardware coverage; they are not claims that those targets currently work.

**Verification:** `cargo build --offline -p palantir --features internals` passed. Small Rust probes confirmed the compiled Linux backend set, default limits, rejection of a synthetic capability profile, and the buffer-growth arithmetic below. Both probe executables completed in under one second. The environment could not open an adapter: Vulkan drivers/libraries could not be loaded, and no alternative backend was compiled for this target. Consequently, no GPU rendering, visual-suite execution, or GPU timing measurements were possible. Findings distinguish source-confirmed behavior from performance opportunities requiring measurement. Some online wgpu pages currently describe 30.0.1; the version-sensitive APIs used below were also checked in the installed 30.0.0 source.

The current shader interface is relatively small: no compute or shader storage buffers, at most two vertex buffers, twelve vertex attributes, ten inter-stage locations, two sampled textures, one sampler, and sixteen bytes of immediate data. This makes a smaller capability profile worth implementing. These observations are a starting point, not a complete certification of a downlevel backend: formats, filtering, shader translation, and presentation also require validation.

## Startup conflates the minimum renderer contract with optional capabilities

- [ ] **G01 — High compatibility impact: the build omits the available OpenGL/GLES fallback.** [Cargo.toml](/home/xxorza/Projects/palantir/Cargo.toml:68) disables wgpu defaults and enables only Vulkan, Metal, and D3D12. The Linux probe reports exactly `Backends(VULKAN)`. A machine with a working GL driver but unavailable Vulkan therefore cannot run this build; an environment override cannot activate an uncompiled backend. Provide an explicitly supported downlevel build/profile using wgpu's existing GLES backend, coupled to the capability work below. Browser coverage additionally needs WebGPU/WebGL features and an asynchronous host/request path; toggling Cargo features alone would not make the current blocking host browser-ready. Wgpu documents desktop GL 3.3+ and GLES 3.0+ as downlevel backends, and its compiled backend set is target-dependent. [Supported platforms](https://github.com/gfx-rs/wgpu#supported-platforms), [enabled_backend_features](https://docs.rs/wgpu/latest/wgpu/struct.Instance.html#method.enabled_backend_features).

- [ ] **G02 — High compatibility impact: negotiation requires limits the renderer does not use.** [DeviceRequirements::against](/home/xxorza/Projects/palantir/src/host/device_requirements.rs:88) starts from `Limits::default()`, changing only resolution and immediate size. A probe using the actual function with otherwise default capabilities, sixteen immediate bytes, and zero storage buffers per shader stage returns “requires 8,” although the production shaders declare no storage buffers. Compute-related defaults are inherited too. Define the renderer's actual minimum limits and request only those, with explicit additional requirements for application GPU callbacks. Wgpu recommends starting with restrictive limits and increasing only what is needed; downlevel capability flags must also be checked when relying on operations outside that baseline. [Limits guidance](https://docs.rs/wgpu/latest/wgpu/struct.Limits.html), [DownlevelCapabilities](https://docs.rs/wgpu/latest/wgpu/struct.DownlevelCapabilities.html).

- [ ] **G03 — Compatibility gap: sixteen bytes of immediate data are a hard requirement instead of an optional fast path.** [DeviceRequirements::FEATURES](/home/xxorza/Projects/palantir/src/host/device_requirements.rs:27), [pipeline layouts](/home/xxorza/Projects/palantir/src/renderer/backend/pipeline_recipe.rs:73), and [the shader prelude](/home/xxorza/Projects/palantir/src/renderer/backend/prelude.wgsl:24) make `IMMEDIATES` universal. An otherwise usable adapter without that feature is rejected. Retain immediates where supported and provide a uniform-buffer variant for the viewport/raster parameters. This particularly matters for browser implementations: wgpu lists native support broadly, including GL emulation, but describes browser support as an evolving proposal. It would be inaccurate to claim this feature excludes all older native GPUs. [IMMEDIATES contract](https://docs.rs/wgpu/latest/wgpu/struct.Features.html#associatedconstant.IMMEDIATES).

- [ ] **G04 — High compatibility impact: every native surface must support COPY_DST.** [Surface configuration](/home/xxorza/Projects/palantir/src/host/winit/gpu/mod.rs:210) rejects surfaces lacking `RENDER_ATTACHMENT | COPY_DST`. The extra usage serves the persistent-backbuffer copy optimization, rather than the ability to draw the UI. Keep copying when supported, and negotiate a presentation path that needs only rendering, such as a full repaint or a textured final pass. Preserve linear blending and the final sRGB conversion when introducing that path. Wgpu guarantees only `RENDER_ATTACHMENT` for surface usage; copy support must be treated as a capability. [SurfaceConfiguration::usage](https://docs.rs/wgpu/latest/wgpu/type.SurfaceConfiguration.html#structfield.usage).

- [ ] **G05 — High compatibility impact: failure of the preferred adapter ends startup without trying another candidate.** [GpuRequest::open](/home/xxorza/Projects/palantir/src/host/gpu_request.rs:99) requests one adapter, then returns immediately if Palantir's requirements or device creation fail. A machine can expose another usable GPU or another backend for the same GPU; the selection request does not include Palantir's later feature/limit checks. Rank native candidates by the requested power policy, check surface and renderer support, and try subsequent candidates after a failure, retaining the diagnostic for each rejected candidate. A software adapter can be a separate availability policy where one is installed. Wgpu exposes adapter enumeration separately from its single-adapter request. [Instance adapter APIs](https://docs.rs/wgpu/latest/wgpu/struct.Instance.html#method.enumerate_adapters).

- [ ] **G06 — Correctness gap: caller-supplied devices are checked against a weaker contract than requested devices.** [DeviceRequirements::met_by](/home/xxorza/Projects/palantir/src/host/device_requirements.rs:137) verifies only immediates and sixteen bytes of immediate storage. It does not validate the pipeline's vertex attributes, vertex buffers, inter-stage interface, or texture-binding requirements. For example, a device with eight allowed vertex attributes passes this check, while the quad and curve layouts require nine and twelve. [OffscreenHostBuilder::build](/home/xxorza/Projects/palantir/src/host/offscreen.rs:165) consequently accepts devices whose first pipeline construction can fail later. Use one complete minimum contract for negotiation and embedding. Validation is against the device's requested limits, even if its adapter supports more. [Device-limit semantics](https://docs.rs/wgpu/latest/wgpu/struct.Limits.html).

## Graphics lifetimes assume the original device and surfaces remain usable

- [ ] **G07 — High robustness impact: device loss has no recovery path.** The host handles [surface acquisition failures](/home/xxorza/Projects/palantir/src/host/winit/window.rs:352), but there is no device-lost callback or device/backend replacement path. Reconfiguring a surface against the same lost device cannot restore its resources. Recovery also needs an ownership design: [ImageRegistry](/home/xxorza/Projects/palantir/src/renderer/image_registry/mod.rs:38) binds its store once, while [ImageHandle](/home/xxorza/Projects/palantir/src/renderer/image_registry/image_handle.rs:27) retains identity and dimensions, not source pixels. Provide host-level loss notification and recreation, including image restoration and application `GpuPaint` resources. Wgpu exposes loss notification, and the graphics contract invalidates the device's resources when the device is lost. [Device callback](https://docs.rs/wgpu/latest/wgpu/struct.Device.html#method.set_device_lost_callback), [WebGPU device loss](https://gpuweb.github.io/gpuweb/#device-loss).

- [ ] **G08 — Android coverage blocker: suspension does not release invalid render surfaces.** [WinitHost's event handler](/home/xxorza/Projects/palantir/src/host/winit/mod.rs:352) creates graphics on the initial `resumed` event, has no `suspended` implementation, and ignores later resumes once the runtime is running. Winit's Android contract requires invalid surfaces to be dropped on suspension and recreated after resumption. A Vulkan or GLES Android port therefore needs a repeatable surface lifecycle around retained application state, not just an additional backend flag. Handle redundant suspend/resume events as well. This is a source-confirmed missing lifecycle, not an Android device reproduction. [Winit lifecycle requirements](https://docs.rs/winit/latest/x86_64-apple-ios/winit/application/trait.ApplicationHandler.html#method.resumed).

## Resource sizing does not consistently respect demand, device limits, and exhaustion

- [ ] **G09 — High correctness impact: buffer growth can exceed max_buffer_size even when the payload fits.** [DynamicBuffer::grow_mapped](/home/xxorza/Projects/palantir/src/renderer/backend/dynamic_buffer.rs:117) rounds the element count to the next power of two without considering the byte limit. Verified using the real 12-byte `MeshVertex`: `16,777,217` vertices need `201,326,604` bytes, below the default `268,435,456`-byte maximum, but growth requests `402,653,184` bytes. [Atlas staging growth](/home/xxorza/Projects/palantir/src/renderer/backend/raster_atlas/mod.rs:531) is also uncapped. Bound growth in bytes, use checked arithmetic, and split uploads/draws when a workload exceeds one buffer. A legal adapter size limit also does not guarantee that an allocation will fit the available memory budget. [Wgpu buffer limits](https://docs.rs/wgpu/latest/wgpu/struct.Limits.html#structfield.max_buffer_size), [AMD memory-budget guidance](https://gpuopen.com/learn/rdna-performance-guide/#memory).

- [ ] **G10 — High correctness impact under pressure: atlas exhaustion drops valid glyphs and icons.** Each [raster-atlas side](/home/xxorza/Projects/palantir/src/renderer/backend/raster_atlas/side.rs:100) has one texture capped by both device dimension and a hard byte budget. When current-frame entries fill it, [text encoding](/home/xxorza/Projects/palantir/src/renderer/backend/text/encode/encoder.rs:125) skips the glyph, and [icon encoding](/home/xxorza/Projects/palantir/src/renderer/backend/icon/mod.rs:160) returns no draw. The 16 MiB side budget is therefore a rendering limit, not merely a cache limit; lower device dimensions make it bind earlier. Introduce an exhaustion policy that preserves output through bounded pages/streaming, or reports an explicit rendering failure. Paging can also avoid the current grow operation's large texture replacement and whole-old-atlas copy inside a frame. Keep total memory bounded across pages and account for resources still in flight. Vendor guidance favors retained/suballocated resources and explicit memory budgets. [AMD resource and memory guidance](https://gpuopen.com/learn/rdna-performance-guide/#memory), [Apple resource lifetime guidance](https://developer.apple.com/library/archive/documentation/3DDrawing/Conceptual/MTLBestPracticesGuide/PersistentObjects.html).

- [ ] **G11 — Memory/performance opportunity: D3D12 inherits a one-million-entry binding allocation policy.** [The default limit request](/home/xxorza/Projects/palantir/src/host/device_requirements.rs:95) leaves `max_non_sampler_bindings` at `1_000_000`, confirmed by the probe. Palantir's built-in pipelines use very small bind groups; image/view count, not this default, should drive the required live binding budget. Expose a bounded application/resource policy and request an appropriate value, leaving room for application GPU content. Wgpu specifically documents a large upfront D3D12 allocation for this limit and warns about RAM use on integrated GPUs. The actual byte cost is device-dependent and was not measured here. [max_non_sampler_bindings](https://docs.rs/wgpu/latest/wgpu/struct.Limits.html#structfield.max_non_sampler_bindings).

## Texture filtering uses the wrong alpha representation or sampling footprint

- [ ] **G12 — Correctness: straight-alpha interpolation still produces transparent-edge fringes.** [Image upload](/home/xxorza/Projects/palantir/src/renderer/backend/image_store.rs:90) preserves straight-alpha texels; [tap](/home/xxorza/Projects/palantir/src/renderer/backend/image_pipeline/image.wgsl:75) bilinearly filters them before [fragment output](/home/xxorza/Projects/palantir/src/renderer/backend/image_pipeline/image.wgsl:202) premultiplies. Halfway between opaque red and transparent black, this produces premultiplied red `0.25` at alpha `0.5`; correct associated-alpha filtering produces red `0.5`. The existing multi-tap path inherits the error because each tap is already filtered. Store/filter associated color in linear space, including mip generation, and define the same alpha contract for `GpuView` composition. This confirms the still-open finding in [the earlier review](/home/xxorza/Projects/palantir/.notes/REVIEW.md). NVIDIA describes this exact fringe failure and why premultiplying after sampling cannot repair it. [GPU Gems: image filtering and premultiplied alpha](https://developer.nvidia.com/gpugems/gpugems2/part-iii-high-quality-rendering/chapter-25-gpu-image-processing-apples-motion), [linear-space mip filtering](https://developer.nvidia.com/blog/texture-tools-exporter-2020-1/).

- [ ] **G13 — Correctness: fract-based tiling cannot replace repeat addressing during filtering.** [The sampler](/home/xxorza/Projects/palantir/src/renderer/backend/texture_binding.rs:60) clamps edges while [the shader](/home/xxorza/Projects/palantir/src/renderer/backend/image_pipeline/image.wgsl:156) wraps only the sample coordinate. The bilinear footprint still clamps its neighboring texels instead of crossing the tile seam. A black/white two-texel tile sampled at the repeat boundary returns the edge color instead of the half-black/half-white blend. Use repeat addressing for tiled draws, retaining clamp behavior for non-tiled crops. This also becomes necessary for a correct repeating mip chain. The earlier review records the same open defect; the API provides distinct clamp and repeat modes. [AddressMode](https://docs.rs/wgpu/latest/wgpu/enum.AddressMode.html).

- [ ] **G14 — Quality/performance opportunity: minified images always sample mip zero.** [Image textures](/home/xxorza/Projects/palantir/src/renderer/backend/image_store.rs:71) have one mip, and [the image shader](/home/xxorza/Projects/palantir/src/renderer/backend/image_pipeline/image.wgsl:75) always uses LOD zero. The default uses a single bilinear tap; the optional footprint path uses up to sixteen bilinear taps per fragment and still sparsely samples footprints wider than its cap. Large images shown as thumbnails or zoomed out therefore trade aliasing for repeated high-resolution texture work. Add a mipmapped path for ordinary minification, building reusable levels when image content changes and selecting the appropriate LOD. Preserve the distinct semantics of nearest sampling and `Peak`; average mipmaps are not a replacement for a maximum-preserving reduction. Measure generation cost, sampling cost, and memory: a complete square mip chain adds about one third to base-level texel storage. Apple identifies mipmaps as a way to improve both minification quality and texture bandwidth. [Apple mipmap guidance](https://developer.apple.com/documentation/metal/improving-texture-sampling-quality-and-performance-with-mipmaps?changes=_5%2C_5).

## Cold resource work executes inside the frame that needs it

- [ ] **G15 — Frame-time risk: a format's twelve pipelines are created synchronously during submit.** [ensure_format](/home/xxorza/Projects/palantir/src/renderer/backend/mod.rs:353) is called from `submit` and constructs the five color families' base/stencil pairs plus two mask pipelines. [PipelineRecipe](/home/xxorza/Projects/palantir/src/renderer/backend/pipeline_recipe.rs:62) always supplies `cache: None`. Existing objects are retained correctly, but the first frame and any first use of another format absorb all compilation work. Prepare known formats when the surface is configured or before interaction starts, and optionally persist a device-keyed pipeline cache on supported backends. Keep cache support optional: wgpu currently implements this facility on Vulkan, not D3D12 or Metal. Validate cold-start and first-format frame times separately from warmed throughput. [Khronos pipeline-management guidance](https://docs.vulkan.org/samples/latest/samples/performance/pipeline_cache/README.html), [wgpu pipeline-cache support](https://docs.rs/wgpu/latest/wgpu/struct.FeaturesWGPU.html#associatedconstant.PIPELINE_CACHE).

- [ ] **G16 — Frame-time risk: filtered-icon prewarming performs an unbounded sweep during upload.** [WgpuBackend::upload_frame](/home/xxorza/Projects/palantir/src/renderer/backend/mod.rs:634) invokes [IconBackend::prewarm](/home/xxorza/Projects/palantir/src/renderer/backend/icon/mod.rs:101). After an icon-set epoch or display-scale change, it walks every loaded set and synchronously rasterizes every filtered icon at its nominal scaled size, including icons the frame does not draw. The work may also grow/upload the atlas and protect those entries before visible batches request their own rasters. Move preparation to an explicit loading/preparation phase or bounded queued work, prioritizing the actual requested raster sizes. Measure the first frame after loading a large filtered set and after changing monitor scale. Creating expensive persistent resources before the render loop is the established practice; calling a sweep “prewarm” does not move its cost off that loop. [Apple persistent-resource guidance](https://developer.apple.com/library/archive/documentation/3DDrawing/Conceptual/MTLBestPracticesGuide/PersistentObjects.html).

## Upload paths copy more data than the draws require

- [ ] **G17 — Concrete transfer reduction: atlas uploads use an unnecessary intermediate GPU buffer.** [flush_pending_uploads](/home/xxorza/Projects/palantir/src/renderer/backend/raster_atlas/mod.rs:443) obtains a mapped staging-belt view through `GpuCtx::write_view`, which records a belt-to-`staging_buf` buffer copy; it then records `staging_buf`-to-texture copies. Wgpu 30 already exposes `StagingBelt::allocate`, returning a slice suitable for direct buffer-to-texture commands. Use that slice directly, with its returned base offset and the required copy alignment, and retire it through the existing submission lifecycle. This removes the intermediate buffer and one copy of the padded upload span while preserving grow-blit-before-new-pixels ordering. It does not require a new dependency or a switch to per-glyph `Queue::write_texture`. Verify command ordering and allocation behavior, then measure upload-heavy text/icon frames. [StagingBelt::allocate](https://docs.rs/wgpu/latest/wgpu/util/struct.StagingBelt.html#method.allocate).

- [ ] **G18 — Transfer/draw-call opportunity: one visible mesh causes all authored mesh geometry to be uploaded.** [upload_frame](/home/xxorza/Projects/palantir/src/renderer/backend/mod.rs:559) passes the full record-store vertex/index arenas into [MeshPipeline::upload](/home/xxorza/Projects/palantir/src/renderer/backend/mesh_pipeline.rs:118). Its guard asks only whether any instances survive; it does not restrict geometry to surviving draws. Static mesh geometry is also copied each painted frame, and repeated copies of the same mesh receive separate spans and [draw calls](/home/xxorza/Projects/palantir/src/renderer/backend/mesh_pipeline.rs:169). A clipped or partially damaged plot with one visible mesh can therefore retain nearly full-scene geometry transfer cost. Upload referenced spans only, or retain geometry by stable identity/content and update only changed payloads; batch repeated compatible instances while preserving painter order. The motivating measurements are uploaded bytes and draw count on repeated meshes and mostly culled mesh scenes. Vendor guidance favors resource reuse and reduced draw/bind overhead. [Apple persistent buffers](https://developer.apple.com/library/archive/documentation/3DDrawing/Conceptual/MTLBestPracticesGuide/PersistentObjects.html), [NVIDIA draw/pipeline guidance](https://developer.nvidia.com/blog/vulkan-dos-donts/).

## Presentation policy assumes one latency and bandwidth tradeoff fits every GPU

- [ ] **G19 — Performance policy: the fixed 40% damage threshold is not a portable cost model.** [DIRECT_PROMOTE_COVERAGE](/home/xxorza/Projects/palantir/src/host/window_driver/mod.rs:200) documents tuning on one Radeon 680M workload. Partial rendering loads the retained target and performs a [full-surface copy](/home/xxorza/Projects/palantir/src/renderer/backend/backbuffer.rs:59); direct rendering clears and repaints. The crossover depends on shader complexity, damage fragmentation, memory bandwidth, and tile architecture, not just damaged area. Direct frames also stale the backbuffer, so alternating above/below the threshold repeatedly forces full resynchronization. Compare complete presentation paths on integrated, discrete, and tile-based GPUs and make the policy configurable or calibrated, with hysteresis if measurements support it. For scale, a 3840 × 2160 RGBA8 copy represents 66,355,200 logical read-plus-write bytes before compression or driver optimizations; this is not a measured DRAM traffic claim. Khronos demonstrates the material bandwidth difference between attachment load/store choices on tiled GPUs. [Render-pass bandwidth guidance](https://docs.vulkan.org/samples/latest/samples/performance/render_passes/README.html).

- [ ] **G20 — Performance policy: frame latency is fixed at one even for throughput-heavy GpuView content.** [Surface configuration](/home/xxorza/Projects/palantir/src/host/winit/gpu/mod.rs:244) always requests `desired_maximum_frame_latency: 1`; the public configuration exposes present mode but no latency policy. Wgpu explicitly describes one as a latency-first setting suitable for light GUIs, and two as a latency/throughput balance. Keep a low-latency default if that is the intended interaction contract, but let applications with substantial GPU callbacks select and measure the alternative. Compare missed refreshes, frame time, and input-to-present latency; increasing buffering is not automatically an improvement. [Wgpu frame-latency guidance](https://docs.rs/wgpu/latest/wgpu/type.SurfaceConfiguration.html#structfield.desired_maximum_frame_latency).

## Hardware evidence needed to validate the performance findings

The following is a proposed validation matrix, not a list of tested configurations. Retain the project's A/B protocol and report cold-frame maxima and steady-state tail latency alongside throughput. GPU pass timestamps alone are insufficient for several findings: the current [main-pass instrumentation](/home/xxorza/Projects/palantir/src/renderer/backend/mod.rs:693) does not encompass atlas uploads, earlier `GpuPaint` passes, or the later backbuffer copy and presentation wait.

| Hardware/backend coverage | Workloads and evidence |
| --- | --- |
| Intel/AMD integrated GPUs; NVIDIA/AMD discrete GPUs; Vulkan and D3D12 where available | Cold pipelines, large mesh uploads, many small updates, multiple windows; allocation peak, submitted bytes, CPU/GPU frame tails, present latency. Compare backends on the same physical GPU where possible. |
| Apple Silicon/Metal; older Intel Macs that remain in the support target | Direct versus retained-target rendering, fragmented partial damage, rounded clips, image minification; complete-frame timing and attachment bandwidth. |
| Oldest supported desktop GL/GLES device or faithful constrained profile | Compile every pipeline and verify all image/atlas formats, filtering, clipping, vertex interfaces, and surface paths against the negotiated minimum. A synthetic limit check alone does not certify this tier. |
| Android Mali/Adreno, if mobile coverage is pursued | Vulkan/GLES capability differences, suspend/resume, memory pressure, filtered-icon preparation, and partial-repaint costs on tiled architectures. |
| Browser WebGPU/WebGL and software adapters, if those fallback targets are pursued | Asynchronous startup, optional-feature fallback, texture/limit validation, complete visual output, and explicit reporting of the selected backend. |

For filtering changes, retain exact image comparisons for transparent edges, tile seams, nearest sampling, ordinary minification, and the distinct `Peak` reduction. For capability/lifetime changes, exercise adapter rejection followed by a successful alternative, device recreation, and surface recreation without losing application state.
